## 概念卡 10：构造失败的空态

**是什么**：构造函数（init/create）失败后，对象必须停在一个可辨识的空态，此后每个操作都能在该状态下安全退化（返回失败或什么都不做），而不是继续按正常态去解引用。
**为什么**：失败是运行时事件，调用方拿到 0 之后没法把对象从代码里删掉，后续的 free/read/write 照样可能被调用。只有让失败路径也留下一个合法状态，才能避免 NULL 解引用和二次释放。
**我代码里的位置**：`parts/05_ringbuf/ringbuf.c` 的 `ringbuf_init`：先把 data/cap/read/write/count 全部清零，再 malloc，失败直接 `return 0`（对象仍是全零空态）；`parts/03_dynbuf/dynbuf.c` 的 `dynbuf_init` 三清零、`dynbuf_free` 归还后再次置空。
**易错点**：init 失败后没清干净，cap 还是传进来的值而 data 是 NULL，后续按 cap 去解引用；"赋过值≠空态"——`data = NULL` 不等于对象已经完成初始化，len、cap、下标都要一起归零；free 之后不置 NULL，重复 free 或重复使用；初始化失败返回 0 之后，还让 `% cap` 这类取模运算的分母保持 0（当前代码是靠 count 为 0 使循环不执行才侥幸没崩，属于"碰巧安全"，不能依赖）。
**面试追问**：
- 问：怎么验证对象真的处在空态？"给字段赋过值"算验收吗？
  答：不算。赋值只是动作，验收要看行为：对空态对象调用每一个公开接口（write/read/append/free，甚至 free 两次），都必须返回失败或安全无操作，不崩不越界。常用做法是失败注入——把 malloc 包一层强制返回 NULL，或者故意传 cap=0，然后把全部接口跑一遍。
- 问：`ringbuf_free` 为什么要把 cap、read、write、count 一起清零，只 free(data) 不够吗？
  答：free 只是把内存还掉，对象里的下标和计数还在，之后任何一次误用的 read/write 都会带着非零的 count/cap 去访问已归还的内存，就是 use-after-free。清零等于给对象打上"不可用"的标记。
