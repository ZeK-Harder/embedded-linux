## 概念卡 8：cap/len 模型

**是什么**：cap 是"已经向系统要到的容量"，len 是"当前真正装了的数据量"，两个字段分开记，写入前用 `len + n > cap` 判断是否需要扩容。
**为什么**：只记 len 就不知道还剩多少可写、该不该重新分配；只记 cap 又不知道数据到哪结束。容量按翻倍增长（16→32→64），是因为那样摊还到每次追加的拷贝成本是 O(1)，每次只加刚刚够的量会退化成 O(n²)。
**我代码里的位置**：`parts/03_dynbuf/dynbuf.h` 的 `struct dynbuf { char *data; size_t len; size_t cap; }`；`parts/03_dynbuf/dynbuf.c` 的 `dynbuf_append` 扩容分支（空给 16，否则 ×2，再用 `while (new_cap < b->len + n)` 补足）。
**易错点**：扩容后忘了同步 `b->cap`，下次判断依据就是错的；比较写成 `>` 而把边界算错；`b->len + n` 可能溢出回绕，稳妥写法是先比 `n > b->cap - b->len`；扩容后的多余容量用完不释放。
**面试追问**：
- 问：为什么 len 和 cap 要同时记，只记一个不行吗？
  答：len 决定数据边界（memcpy 写在哪、对外报多长），cap 决定分配边界（还剩多少空间、何时扩容），回答的是两个不同问题。只有 len 就得每次去猜剩余空间，只有 cap 就不知道末尾在哪。
- 问：为什么翻倍扩容而不是每次 +n？
  答：翻倍时总拷贝量是 16+32+…+2^k ≈ 2·2^k，摊还到每次追加是 O(1)；每次只补够用的量，n 次追加要拷 1+2+…+n = O(n²)，数据量一大性能就塌。
